## Follow-up: root cause and fix-system-font-crash (same day, branch fix/coretext-font)

### Root cause (confirmed statically and on the device)
Static analysis covers Ghidra and strings of `lib/armeabi-v7a/libCoreGraphics.so` (1.7.6 sha256 `4eb72cc1...`; 1.7.4/1.7.5 `f35d9126...`) and the phone's own `/system/etc/fonts.xml` and `/system/fonts`.
- `_CGFontDBCreateSystem` (0xc29a4), run once via `CGFontDBGetLocal`, parses `/system/etc/fallback_fonts.xml` and `/vendor/etc/fallback_fonts.xml` (both missing on Android 14), then `/system/etc/fonts.xml`, else `/system/etc/system_fonts.xml`, else a hard-coded Droid* list.
- The parser (0xc2b7c, libxml2 `xmlTextReader`, element `font` for fonts.xml) keeps the FIRST text node of each `<font>` without trimming it. It formats `/system/fonts/%s`, and 0xc3758 `stat()`s the path before it calls `FcConfigAppFontAddFile` + `CGFontDBAddFontsAtPath`.
- On this phone, all 36 `Roboto-Regular.ttf` entries have `<axis>` children. The text node is therefore `"Roboto-Regular.ttf\n          "`, the stat fails, and Roboto is never registered. (The file is also a variable font with `fvar`/`gvar`/`HVAR`/`avar`.) No `NotoSans-{Regular,Bold,Italic}` file exists. `DroidSans.ttf` is a symlink to Roboto, but fonts.xml does not list it.
- `_CGFontDBCreateSystemFontNamesSubstitutions` (0xbd484) picks the regular face as the first registered of NotoSans-Regular / Roboto-Regular / DroidSans, defaulting to `NotoSans-Regular`. Bold and italic work the same way and default to `NotoSans-Bold` / `NotoSans-Italic`. Hundreds of names (Helvetica*, HelveticaNeue*, Roboto-*) map onto these three.
- `CGFontDBGetFontWithName` (0xbd274) tries the name tables, then the substitution, then `RobotoCondensed-Bold`, then `NotoSans-Bold`. When all of them miss it returns NULL. `CTFontCreateWithName` wraps that NULL and `CGFontCopyName(NULL)` reads +8 = SIGSEGV at fault addr 0x8. Both crash sites (IAP list, CoreText default font in world text layout) take this path.

### Fix
`fix-system-font-crash` (recommended, every game version): adds static, unhinted subsets of Noto Sans 2.015 Regular, Bold and Italic to `assets/`. The subsets cover Latin, Greek, Cyrillic and Vietnamese, about 200 KB each, under SIL OFL 1.1 (`packages/core/src/patches/fonts/OFL.txt`, generated by `scripts/fonts/noto-sans-subset.py`). The patch lists the three files first in `UIAppFonts` of `assets/Info.plist`, which the game's UIKit registers at start-up. Their PostScript names are exactly the substitution defaults, so every system-font lookup resolves. Where the system fonts are found, the substitutions prefer them.
The PC port (blockheads-pc, `bhpc-vfs`) works for the same reason: it serves an Android-4.4-style `system_fonts.xml` and bundles Liberation Sans for each referenced file name.
Not chosen:
- a native null guard: it would need hash-pinned edits in two libraries per version and would draw no text;
- a parser trim: it would feed a variable font to a 2015 FreeType/Skia.

## Follow-up: raise-target-sdk at 28 and gamepad-controls (same day, branch feat/gamepad)

Folded (cover screen 904x2316), Wi-Fi adb, builds from `scripts/device-test/build.ts` with fix-system-font-crash,
fix-config-change-crash and fix-welcome-popup-deadlock as the base.

### raise-target-sdk now targets 28
- `getprop ro.build.version.min_supported_target_sdk` = 28 on this phone: Android 14 shows the "built for an older version"
  dialog only below 28, so 28 is enough for the patch's goal.
- At 28 the `max-target-p` hidden-API list is still allowed: `dumpsys package` shows targetSdk=28; the game starts, the
  menu renders, a world loads ("loading world with size"), walking and menus work; no `hiddenapi`, `JNI DETECTED`,
  `Fatal signal` or `FATAL EXCEPTION` in logcat. 29 stays impossible without replacing Apportable's native
  `View.setFrame(IIII)Z` lookup, so the target was lowered instead (and `requestLegacyExternalStorage`, which only matters
  from 29, is no longer written). Still opt-in: one phone, one session.

### gamepad-controls (opt-in)
No physical controller was available. A virtual one was created with Android's `uinput` shell command (JSON
`register` + `inject` of evdev events, vid/pid 045e:02ea, so the system's Xbox key layout applies: Android sees
`KEYBOARD | GAMEPAD | JOYSTICK`, BTN_* as KEYCODE_BUTTON_*, ABS_X/Y left stick, ABS_RX/RY mapped to AXIS_Z/RZ, HAT as
AXIS_HAT_X/Y). `input gamepad keyevent KEYCODE_DPAD_*` was used for the d-pad keys.

| input | result |
|---|---|
| right stick, hat, d-pad keys | cursor ring appears, moves, stays inside the screen, hides ~3 s after the last input |
| A in menus | taps at the cursor: Play (world loads), Options, Customize, Warp In, pause-menu buttons, crystal store, Help |
| A in the world | tap on an adjacent dirt block digs it (inventory dirt +1); tap on the portal opens it; tap on the portrait opens the blockhead panel |
| A held 4-5 s on a non-adjacent block | touch held, released on button up, nothing dug (game rule: only reachable blocks) |
| left stick right / left | blockhead walks while the stick is held; the camera follows once the blockhead was selected via its portrait. Walking left past the portal the held touch hit the portal and opened its menu (the touch is a normal tap; objects at head height beside the blockhead are interacted with) |
| B / Start | Back: opens and closes the pause menu; closes the help web view (that activity gets Android's own BUTTON_B -> BACK fallback) |
| L1 / R1 | two-finger pinch out / in, one zoom step each |
| Y | cycles: in, in, out x4 (zoomed in twice, then far out) |
| device removed (uinput exit) | no crash; touches released |

Not verified: a real Bluetooth/USB controller (axis ranges, which axes a given pad uses for the right stick, analog
triggers), R3 (same code path as Y), long play sessions, the unfolded screen. Once, during a 5 s A hold, the game's pause
menu appeared without a Back press; it did not happen again in later holds and the cause is unknown.

At the end the all-recommended build is installed again.
